## 2. NSPL loader → BatchWriteItem

The August vintage roll is due within weeks and would otherwise have paid the measured **5.80
hours** again. `_flush_batch` now chunks into 25-item `BatchWriteItem` requests, removing ~96% of
the signed round trips the previous load was bound by.

**The next full load is unmeasured.** Expect well under an hour; do not quote a figure until a real
run produces one. This docstring was already wrong by 10×, in the optimistic direction, for exactly
this reason.

**The `UnprocessedItems` retry loop is load-bearing, not defensive.** `BatchWriteItem` reports
partial failure as an **HTTP 200 with a non-empty `UnprocessedItems` map**, never as an exception,
so boto3's adaptive retry — the layer already absorbing throttling here — cannot observe it.
Dropping that map loses rows *while `run_load` still credits them to `written` and checkpoints past
them*, which is unrecoverable because a resume starts after rows that never landed. Same class of
silent shortfall as the checkpoint-ahead-of-writes bug fixed on 25 Jul. Exhausting the retries is
therefore deliberately fatal.

**It degrades automatically.** On `AccessDeniedException` it latches back to the per-item path and
completes at the old speed, so it is safe to run either side of the IAM change. **A roll that still
takes ~6 hours is the signal the grant never landed.** A `ValidationException` — most plausibly a
duplicate postcode inside one 25-item window, which fails the whole request where `PutItem` would
simply overwrite — falls back for that chunk only, without latching.

Five tests in `tests/test_load_nspl.py::TestBatchWritePath`, every one covering a way the swap could
lose rows *while still reporting success*. Root suite 140 → **145**.

## 5. Batch metering — decision documented, still open

`BATCH_METERING_DECISION.md`, with every figure read from `template.yaml` and `score/app.py` rather
than from memory.

API Gateway meters **requests**; the product sells **scores**. Quota 1,000/month ×
`MAX_BATCH_SIZE` 100 = **100,000 free scores/month** — the volume the £499 Professional tier exists
to sell.

**Newly noted, and the part not previously written down: the quota is monthly but the throttle is
per second.** At 2 req/s with 100 queries each, a single free key drains the entire monthly
allowance in **about eight and a half minutes**. That is a burst, not a drip; it is over before any
alarm with a monthly window notices, and the $20 billing alarm is not positioned to catch it.

Five options are laid out. The recommendation is that the launch blocker is **not** building a
metering subsystem — it is **deciding what the free tier may be worth**, which is one line in
`template.yaml` (`Quota.Limit: 100` → 10,000 scores/month) and shippable before any pilot signs,
with in-Lambda score metering deferred until a paying customer justifies operating it.

**Bill deferred the decision on 27 Jul.** It is **not** blocked by the lockout — `flightmap-dev`
still deploys normally, so this ships the moment a number is chosen.

## 6. Two quality-gate defects found, neither fixed

**`npm run format:check` fails on `index.html`.** Pre-existing and byte-identical at `origin/master`.
Left alone deliberately: reformatting an 8,200-line hand-maintained, deployed file is a decision, not
a cleanup task. Preflight therefore does **not** currently pass end-to-end, and has not for some time.

**The Playwright e2e suite reports false failures at default concurrency.** It returned **14 failed /
2 passed (55.3s)**; the same suite at `--workers=2` returned **16 passed (13.9s)**, and a single
"failing" test passed in isolation in 2.9s. Cause: `fullyParallel: true` with no worker cap against
`baseURL` = the **live CloudFront site**, so the parallel burst produces timeouts indistinguishable
from real assertion failures. The captured page snapshot showing a perfectly rendered page is the
tell. `workers: 2` was deliberately **not** committed — one run cannot distinguish CloudFront
throttling from local contention, and pinning it would slow every future run for a cause that may be
this machine only.

**Two shell traps worth not repeating.** `make` is not on PATH in Git Bash here, so `make preflight`
"succeeded" only because it was piped to `tail` — a pipeline reports the *last* stage's status. Read
the output, or use `${PIPESTATUS[0]}`.
