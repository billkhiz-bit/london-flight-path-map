The 57 checks, and how the coding assistant reaches Amazon

A companion to "How Sky Score works, in plain English" · 2026-09-21

In one breath: before any change to Sky Score is saved, 57 automatic checks run; 45 of them can refuse the change. Most of the code was written with a coding assistant, which reaches Amazon only through a pass that is allowed to touch Sky Score's own things and nothing else. The checks are what make that arrangement safe; the pass is what makes it limited.

1 - What "preflight" is

Preflight is a checklist that runs on my computer before any change to the project is saved into its history. One command runs all 57 in sequence and prints one line per check: PASS, or FAIL with the reason.

  • 45 are blocking. If one fails, the change cannot be saved until it is fixed. There is no "save anyway" button; the rule in the project's own notes says a failing check must be fixed, not skipped, even if I ask.
  • 12 are advisory. They print a warning and let the change through. They are advisory for a reason each: some compare the live website with the working copy (which differ by design until the next deploy), and some need large data files that a fresh copy of the project would not have.
  • It takes about 24 minutes when the flood-map cache is cold, about 15 when warm. Most of that is a robot driving the real website in a real browser at eleven screen sizes, and the checks that phone a government service to compare a number.
  • Six stages need the internet. They can be skipped for an offline run, but a skipped stage still prints its own line saying SKIPPED, and the final verdict says "PASS (INCOMPLETE)". A stage that vanishes from a report is indistinguishable from one that passed; that was a real bug once.

3 - The rule that makes the checks worth having

A check that has never gone red has not been tested. Before a new check is trusted, the thing it guards is broken on purpose, the check is watched turning red, the break is undone, and the check is watched turning green. Only then does it count.

The rule exists because twelve checks in this project's history were green for months while checking nothing. Nobody switched them off; each decayed one sensible decision at a time:

  • The whole checklist once piped every result through a command that always succeeds, so it said PASS while running nothing.
  • The accessibility scan covered one page in nine and only the most severe faults; every real fault was one grade lower.
  • A minimum of "at least 17 files" was left in place the day after the 18th file was added, so it could no longer notice that one going missing.
  • A test took its expected answers from the very list it was testing, so the two could never disagree.
  • A test file that guarded "the fallback shipped untested" was itself in no runner at all.

The question that finds these is not "what does this check run?" but "what would this check miss?". Names are treated as claims: a check called "all pages" that scans one page is the warning sign.

4 - How the coding assistant reaches Amazon

Most of the code was written with Claude Code, a coding assistant that reads and writes the project's files under direction. It runs on my computer, not on Amazon. When it needs to touch the live system, here is the path, and where it is narrow.

1  Me, at the keyboardI give the instruction. Nothing below happens without one, and going live needs an explicit "go".
↓
2  Claude Code, on my laptopReads and edits files, runs the checks, runs commands in the terminal. It has no account of its own with Amazon.
↓runs a command such as "upload this file" or "deploy the blueprint"
3  Two guards on every commandA screening hook blocks destructive commands outright (delete, force-overwrite, wipe). Claude Code's own safety classifier refuses commands it judges to be a production deploy unless I run them myself. Both have fired for real; see Part 7.
↓
4  Amazon's command-line tools, using a named passThe command runs Amazon's own tools (the AWS CLI, and SAM for the blueprint) with a pass called "flightmap" that lives in a file on my laptop, outside the project, never in the code.
↓over the internet, to Amazon's London region
5  Amazon checks the pass against its written permission listThe pass belongs to one identity ("flightmap-dev") with one written list of what it may do. Every command is checked against that list before anything happens.
↓
6  Only Sky Score's own thingsMost of the list is restricted to things named "london-flight-map-*": the eight workers, the five card boxes, the one blueprint, the one website bucket. Two parts are wider than that, and are described honestly below.

What the pass cannot do, and where it can do more than it should

  • Edit its own list directly. When a new permission is needed, I paste it in through Amazon's web console myself, which needs my password and my phone. But this is not yet a hard wall, and I would rather say so. To deploy the workers, the pass may create worker roles and attach permissions to them, and nothing yet limits which permissions. A determined holder of the pass could use that to give a new role far more than Sky Score needs. Closing it is written down as an open item (a "permissions boundary"); it waits for a console session because an untested change to these rules caused a real outage once already.
  • A second wide grant. The part of the list that manages the web front door (API Gateway) covers every such front door in the London region, not only Sky Score's. There is only one today, but the list does not enforce that.
  • Use the web console at all. The pass is for command-line tools only. The console is mine, protected by a second factor on my phone.
  • See the bill, other projects, or other people's accounts. Not on the list, though the gap in the first point is a way round that until it is closed. Other people's accounts are out of reach either way.
  • Empty a card box or delete the website bucket. The screening hook blocks delete commands before they reach Amazon, and the list keeps deletions to Sky Score's own named things even if one got through.

Where the secrets live

  • The Amazon pass: a file in my home folder, outside the project. Never copied into the code.
  • The API keys and the government energy-data token: a file called .env in the project folder that the version history is told to ignore. The energy token is handed to the blueprint at deploy time as a hidden value, so it never appears in Amazon's own records of the deploy.
  • If a secret ever appears in a chat log or a terminal, it is treated as burned and replaced. There is a script for replacing the energy token that refuses to run with the old value.
  • The automated tests that run on GitHub have no Amazon pass at all. They lint and test; they cannot deploy. Nothing reaches the live system except from my laptop, on my instruction.

5 - Five layers of guardrail

  1. The 57 checks. Nothing is saved into the project until they pass, and a saved change is the only kind that gets deployed.
  2. The screening hook. Every terminal command the assistant proposes is read first; destructive ones are blocked before they run.
  3. The safety classifier. The assistant's own judgement of "this looks like a production deploy", which makes it stop and hand the command to me.
  4. The written permission list on Amazon's side. Even a command that gets past everything above can only touch Sky Score's own named things.
  5. My go-ahead. The working rule: the assistant deploys nothing without an explicit instruction, and a deploy is verified afterwards from the live address, never from the command's own "success" message.

The layers are deliberately different in kind: a checklist, a filter, a judgement, a permission, a person. A single guardrail, however good, has one way to fail.

6 - What a deploy looks like, step by step

  1. Preflight passes (Part 1) and the change is saved into the project's history.
  2. Back end first. SAM reads the blueprint, works out what would change ("change set"), and applies it. Only the workers whose code changed are replaced. If a data edition rolled, the API must go live before the website, so the site's copy of the numbers is never ahead of the API's.
  3. Then the website, from a deploy file with one named target per surface (fonts, pages, data, app files, demo, the 100 borough pages, and now the talk write-ups). The order inside it matters: data files before the page that fetches them, fonts before the offline worker that pre-caches them.
  4. Then the caches are cleared at the copies-in-every-city, so visitors get the new version and not last hour's.
  5. Then verify from the origin. Download the live files and compare with what was written (check 54). Ask the live API for the 28 postcodes (check 8). A deploy is done when the live address says so, not when the upload command said "complete". On 26 August every upload succeeded and the cache-clear failed at the very end; the deploy looked done and was not.

7 - Two days the guardrails said no

16 September. A data release morning: the Land Registry's July prices, a methodology change, two defects found by the checks. When it came to the back-end deploy, the assistant's safety classifier refused to run it from its own session. I ran the one deploy command myself. That is the arrangement working as designed: the assistant prepared and verified everything up to the line, and the line held.

21 September, the day this was written. After uploading the plain-English write-up to the site, the assistant tried to fetch the live address to compare the file's fingerprint with the original. The classifier refused that too, judging the fetch to be part of the deploy. So the assistant stopped, said what it had tried to do and why, and asked me to run the one-line check. Thirty seconds of my time, and the rule stayed a rule rather than becoming a rule with exceptions.

What the second day shows. A guardrail that only ever blocks the dangerous thing is easy to keep. One that sometimes blocks a harmless thing is the kind you are tempted to loosen. Keeping it costs a little friction on ordinary days; loosening it costs the one day it mattered.
